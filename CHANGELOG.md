# Changelog

Notable changes to Roost's packages and kernel library releases. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow SemVer 2. A release moves the `Unreleased` entries under `## [<version>] - <YYYY-MM-DD>`; the release workflow refuses a tag without that section and uses it as the release notes ([docs/releasing.md](docs/releasing.md)).

## [Unreleased]

Nothing has been released yet. The first release is Preview 1 (build plan R-062).

### Security

- SDK 10.0.403 and .NET 10.0.14, for CVE-2026-111497 (GHSA-p3jp-9v83-76w9, a Brotli decoder out-of-bounds write). `roost` and `roost-worker` compile with `Microsoft.DotNet.ILCompiler`, and NuGet audit refused 10.0.12 at restore.

### Fixed

- `POST /v1/embeddings` on e5 refuses an input over 512 tokens as `prompt_too_long` naming `input[i]`, as EmbeddingGemma 2 and GLiNER2 do. It was silently truncated.
- `Starlings.Roost.Server` refuses web pages by `Host` and `Origin`, with `--allowed-host` for other names. On a loopback listener a page in a local browser can no longer drive the server or read its answers through DNS rebinding; a non-loopback listener needs `--allowed-host` for the same protection (#157).
- `POST /v1/responses`: `metadata` and `user` are limited, and a stored response drops its prompt when it ends, so finished responses can no longer fill the store with data no route returns (#157). The body-size limit still applies while a response is running.
- An oversized body, and text that is not valid Unicode, answer 4xx rather than a 500 and an error log (#157).
- A weights path over 4096 UTF-8 bytes is refused, and every shorter one now fits the plan buffer, so `POST /update_weights` no longer loses a healthy worker over its path (#157).
- `roost serve` reports a corrupt `tokenizer.json`, or a listen address it can't bind, as an error and exit code 1, and `roost doctor` reports the tokenizer as a failed check (#157).
- A worker that exits during startup keeps its output: `ProcessWorkerTransport` reads the end of the worker's streams before it reports the failure, so the error no longer loses the lines that explain it (#158).

### Added

- roost-v1 onboarding plugin (R-055, partial), a tool in `evidence/pipeline/onboarding/` that never ships in the runtime: `roost-onboard inspect` maps a Hugging Face config.json to the C3 op vocabulary and C4 state groups (full, sliding-window, Gated DeltaNet recurrent, MLA latent, optional expert group) and reports a typed JSON verdict (`composes`, `composes_pending_reference` or `missing_ops`) with a status per op (`available`, `declared`, `gap`, `missing`), the load transforms a definition needs and its assumptions; `roost-onboard validate-recipe` checks recipes against the strict roost-v1 recipe schema and the rules beyond it. First recipe `evidence/recipes/qwen3.5-0.8b.json` (the existing profile, `experimental`). Tested on hand-written configs of Qwen3, Qwen3.5, Qwen3-MoE, Gemma 3 and DeepSeek-V3; capabilities `untested`. Onboarding three unseen models (M3 gate, R-057) is open.
- Sleep, wake and in-place weight update, CPU half (R-100), with contract version 6 and shared-memory layout 3: C8 gains the control messages `ROOST_RING_SLOT_SLEEP`, `_WAKE` and `_REPLACE_WEIGHTS` with `RoostControlMessage` and `RoostControlResult`, and `ROOST_WORKER_SLEEPING`. `Starlings.Roost.WorkerHost`: `ControlMessages`, `IWeightLifecycle`, and `WorkerRuntime` handling them over both transports (steps refused while asleep, each message timed). `Starlings.Roost.Worker`: `HostWeightResidency` releases, restores and replaces host weights through the R-024 verified stream, so a substituted file fails the wake or the replacement and a failed replacement keeps the old weights. `Starlings.Generation.Roost`: `RoostChatClient.SleepAsync` (KV cache, or KV cache and weights), `WakeUpAsync` (digest-checked, wake time in `LastWakeDuration`), `UpdateWeightsAsync` (from a locked file), `IsSleeping`, capabilities `sleep_wake` and `weight_update` (`untested` on the CPU path, `unsupported` for the packaged CUDA worker, which refuses them with `ProfileUnsupported`). `Starlings.Roost.Server`: `POST /sleep`, `POST /wake_up`, `GET /is_sleeping` and `POST /update_weights` with `--enable-sleep-mode` (off by default), loopback clients only. Tested with roost-tiny-hybrid on `CpuOps`; no GPU evidence.
- Async scheduling, engine and CPU half (R-032), with contract version 5 and shared-memory layout 2: C2 gains `ROOST_SEQ_FLAG_SAMPLED_INPUT` (`SequenceOptions.SampledInput`) and `RoostStepPlanHeader.input_step_id`, a decode row whose input is the id the worker sampled in the previous step. `Starlings.Roost.Engine`: `PlannerOptions.AsyncScheduling` builds plan N+1 while step N runs, with lengths enforced at plan time and stop ids applied one step late. `Starlings.Roost.Worker`: `PlanLimits.SampledInputs` and `SampledInputPatcher` for a CPU worker; the CUDA worker refuses such plans until device-side patching (stream F). `Starlings.Generation.Roost`: `RoostWorkerOptions.AsyncScheduling` keeps two steps published and hides the stop lag; capability `async_scheduling` is `untested` with it and `unsupported` without. A layout 1 worker now refuses the handshake.
- Sampler, CPU half (R-042), with contract version 4 and C1 ABI 1.3: C3 `SampleArgs` and C1 `RoostSampleParams` gain repetition, presence and frequency penalties over per-row token counts and a prompt mask, stop flags against per-row stop ids, top-k logprob ids and values, and a math mode (`SampleMath.Reference` or `SampleMath.Fp32`, the float32 definition a GPU sampler must match bit for bit). `CpuOps.Sample` implements them; `CudaOps.Sample` refuses every call until a kernel exists. `Starlings.Roost.Worker` adds `HostSampler` (the CPU sampler with per-sequence token history), `PlanLimits.Sampling` and logprob rows in `StepResultWriter`. `Starlings.Generation.Roost` adds `RoostWorkerOptions.Sampler`: with `RoostSampler.Cpu` the client accepts temperature, top-p, top-k, min-p, seed, penalties, logprobs and top logprobs (`min_p`, `repetition_penalty`, `logprobs`, `top_logprobs` as additional properties) and returns logprobs as `RoostTokenLogprob` entries on the updates; `sampling`, `penalties` and `logprobs` are `untested` there and stay `unsupported` on the CUDA worker. The loader now needs kernel libraries built for ABI 1.3.

### Changed

- Starling pins raised to `[0.5.0]` and `Starlings.Tokenizers` to `[0.3.4]` (#156). `Starlings.Roost.Generation` now references `Starlings.Generation.Abstractions` and the definition packages `Starlings.Models.Qwen35` and `Starlings.Models.QwenChat` in place of `Starlings.Generation.OnnxGenAI`, so `Starlings.Roost.Generation` and `Starlings.Generation.Roost` no longer bring ONNX Runtime GenAI. `Microsoft.ML.OnnxRuntime` stays in `Server`, for the pooling models. The floor of `Microsoft.Extensions.AI.Abstractions` rises from 9.8.0 to 10.10.1, the minimum `Starlings.Generation.Abstractions` requires.
- `Starlings.Tokenizers` is a direct, exact pin (`[0.3.4]`, the version the Starling 0.5.0 packages require) in `Starlings.Generation.Roost` and `Starlings.Roost.Generation`, because `Starlings.Tokenizers.Tokenizer` is in the public API (`RoostModelProfile`); it was only transitive before, so `tools/check-roost-boundaries.py` never saw it.
- `Starlings.Roost.Generation`: `Qwen35RoostChatTemplate` builds a `Qwen35ToolCall` from the cloned arguments element directly instead of enumerating and re-serialising its properties. Same rendering.
- Documentation: the generation layer's status, build plan section 3.1 and its section 12 risk, and the kickoff log record that Starling published `Starlings.Models.QwenChat`, `Starlings.Models.Kev` and the public `StopSequenceMatcher` in ai-dotnet 0.3.0 (starling#124), and that `RoostCapabilities` carries `stop_sequences` as `untested`; `evidence/registry/README.md` states what the Qwen3.5-0.8B admission records for the tokenizer asset (`report_to_starling.status = "not needed"`).
