# Changelog

Notable changes to Roost's packages and kernel library releases. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow SemVer 2. A release moves the `Unreleased` entries under `## [<version>] - <YYYY-MM-DD>`; the release workflow refuses a tag without that section and uses it as the release notes ([docs/releasing.md](docs/releasing.md)).

## [Unreleased]

Nothing has been released yet. The first release is Preview 1 (build plan R-062).

### Added

- Release workflow (`.github/workflows/release.yml`), kernel release build (`tools/release-kernels.sh`) and release drill (`tools/release-drill.sh`) (R-060).
- `Starlings.Roost.Generation`: `Qwen3RoostChatTemplate`, the Qwen3 template over Starling's published `QwenChatTemplate` (`QwenChatProfile.Qwen3`, text only, `enable_thinking=false`; experimental), with `Starlings.Models.QwenChat` pinned exactly at `[0.3.0]` (host side only, decision 30). Completes R-009.
- `Starlings.Roost.Ops`: `CpuOps` implements the MoE ops MoeRouteTopK, MoePermute, MoeUnpermute, GroupedGemm and FusedMoe (R-080, CPU half): double-precision references with deterministic tie order (lower expert first), a stable permutation and FusedMoe as the composition of the unfused ops; bf16, fp16 and fp32 weights, FP8 and INT4 `unsupported`. No GPU variant exists yet (`untested`).
- `roost-tiny-moe` (`Starlings.Roost.Models.Tiny`, test and CI only): a Qwen3-MoE-shaped tiny model with seeded weights, run on `CpuOps` in CI.
- `Starlings.Roost.Ops`: CPU references of `Quantize`, `Dequantize`, `GemmFp8` and `GemmW4A16`, FP8 E4M3 and E5M2 element support (round to nearest even, saturating) in `CpuOps` including an FP8 KV cache through `CacheWrite` and `PagedAttention` (unit scale only), and `Int4Weights` (AWQ and GPTQ scale and zero-point rules and checkpoint packing). CPU half only; no GPU kernel, fidelity profile or admission yet (R-077, R-043; `src/Starlings.Roost.Ops/STATUS.md`).
- Co-tenant admission, CPU-tested part (R-044): `Starlings.Roost.Engine` adds `PolledDeviceMemorySource`, an `IDeviceMemorySource` that re-reads an `IDeviceMemoryReader` every 2 seconds on a background timer and serves a cached reading without blocking, with a typed `DeviceMemoryReadStatus` (library missing, device not found, device lost, failed, stale) instead of an exception; `Starlings.Roost.Cuda` adds `INvmlApi` and `NvmlApi` over the generated NVML bindings; `Starlings.Roost.Worker` adds `NvmlDeviceMemoryReader` (by NVML index or UUID, `nvmlDeviceGetMemoryInfo_v2` with a v1 fallback, handle re-lookup after a lost device). `Starlings.Generation.Roost`: `RoostWorkerOptions.DeviceMemory` and `MinFreeDeviceBytes` refuse a new request with `InsufficientDeviceMemory` while free memory is below the floor, never aborting running requests; `RoostCapabilities` lists `co_tenant_admission` as `untested`. No NVML source is the default yet (the reader is worker-side code a host package may not name, decision 21), and the co-tenant GPU test is open.
- `Starlings.Roost.Kernels` (R-072, partial): `VariantSelector` chooses among conformance-qualified variants per shape bucket and SM (`ShapeBucket`, `VariantCandidate`, `VariantQualification`), refusing with `ProfileUnsupportedException` when none qualifies, with ordinal tie-breaking; `AutotuneCache` persists medians keyed by SM, driver, shape bucket and variant digest in a versioned JSON file with atomic saves and corrupt-file tolerance. CPU-tested only; `experimental` and not wired into the worker (`src/Starlings.Roost.Kernels/STATUS.md`).
- `Starlings.Roost.Kernels`: `KernelLibraryResolver` fetches the per-SM kernel library of the package version from the GitHub release through `Starlings.Acquisition`, verified by size and SHA-256 against the embedded manifest (decision 12); `KernelManifest.Embedded()`.
- `Starlings.Roost.Server` and the `roost` executable (R-037, partial): `POST /v1/chat/completions` and `POST /v1/completions` (whole or SSE with `data: [DONE]`) and `GET /v1/models` over `RoostChatClient`; one error body for every failure; unknown and unsupported options are a 400 naming the option; loopback only unless `--allow-non-loopback`; client disconnect cancels the generation. CPU-tested only; every route is `untested` (`src/Starlings.Roost.Server/STATUS.md`).
- `Starlings.Generation.Roost`: `RoostChatClient.GetCompletionAsync` and `GetStreamingCompletionAsync` complete a raw prompt without the chat template (capability `raw_completion`, `untested`).
- `Starlings.Roost.Server` (R-074, partial): the OpenAI Responses API (`POST /v1/responses` whole, streamed with the Responses events, or in the background; `GET /v1/responses/{id}`; `POST /v1/responses/{id}/cancel`) over an in-memory store bounded by `RoostServerOptions.ResponseStoreCapacity` (1024) with expiry `ResponseStoreTtl` (one hour); the Anthropic Messages API (`POST /v1/messages` whole or streamed, `POST /v1/messages/count_tokens`) with Anthropic's error body naming refused fields; vLLM's `POST /tokenize` and `POST /detokenize` bodies; `GET /health`, `GET`/`POST /ping`, `GET /version` and `GET /ready`. vLLM's `prompt_embeds` is refused by name (no embedding input in `RoostChatClient`). CPU-tested only; every route is `untested` (`src/Starlings.Roost.Server/STATUS.md`).
- Metrics, traces and log hygiene (R-038, partial): `Starlings.Generation.Roost` adds `RoostTelemetry` (`RoostChatClient.Telemetry`), a `Meter` named `Starlings.Roost` per client with request counts by finish reason, prompt and generated token counters and histograms, time to first token, inter-token and end-to-end latency histograms, running and waiting request gauges and the KV block usage gauge, plus one `roost.request` activity per request tagged with its id, token counts and finish reason, never its text (capability `telemetry`, `untested`). `Starlings.Roost.Server` serves `GET /metrics` in Prometheus text format from its own writer (no new package), each family under a `roost_` name and under vLLM's `vllm:` names with the `model_name` label. A test scans every log category at `Trace` for prompt and reply text. CPU-tested only (`src/Starlings.Roost.Server/STATUS.md`).

- Tool-call and reasoning parsers (R-053, partial): `Starlings.Generation.Roost` renders `ChatOptions.Tools` (`AIFunction` declarations) and the new `RoostChatClient.EnableThinkingProperty` (`enable_thinking`) through the chat template, and parses the completion incrementally into `FunctionCallContent` (finish reason `ToolCalls`) and `TextReasoningContent`: the Qwen3.5 format through Starling's published `Qwen35ToolCallParser`, Hermes (`<tool_call>` JSON) and Qwen think blocks. `RoostModelProfile.ToolCallFormat` and `ReasoningFormat` (null: from the chat template). Assistant `FunctionCallContent` and tool-message `FunctionResultContent` are rendered into the conversation. A required tool call and `AllowMultipleToolCalls` false are refused; the Qwen3 template still refuses tools and thinking. `Starlings.Roost.Server`: `tools`, `tool_choice`, `parallel_tool_calls`, `chat_template_kwargs.enable_thinking`, assistant `tool_calls` and `reasoning_content` and `tool` messages on `POST /v1/chat/completions`, answered with `tool_calls` and `reasoning_content`, whole and streamed. Capabilities `tools` and `reasoning` are `untested` (CPU tests on a local corpus of template renderings; P-029 is not in this repository).
- API compatibility suite (R-040, partial): `tests/Starlings.Roost.ApiCompat.Tests` drives `Starlings.Roost.Server` on Kestrel over the scripted worker with the official OpenAI .NET client (`OpenAI` 2.14.0, exact pin, test only): chat completions whole and streamed, tool calls and `reasoning_content`, the Responses API (whole, streamed, background, retrieve, cancel), models and error bodies, and every unsupported option the client can set refused with a 400 naming it. `tests/tools/api_compat/openai_compat.py` runs the same kind of checks, plus `/v1/completions`, with the official openai Python package (3.35.1), opt-in (`ROOST_API_COMPAT_PYTHON=1`) or against a running `roost serve`. Capability row `untested`: no client has run against a GPU.
- Structured output, CPU side (R-051, partial): `native/roost-grammar`, a Rust crate (source and `Cargo.lock` only, decision 22) that puts llguidance (`guidance-ai/llguidance` at `6cef6ed9c973c2a155a85f2bb1996320af28b289`, MIT) behind Roost's C ABI 1.0 (`include/roost_grammar.h`): tokenizer environments with the model's stop ids and logits width, JSON-schema, JSON-object, regex and Lark matchers, next-token masks, consume, accept and stop states, typed status codes. `Starlings.Roost.Native` (new, worker-side, in `Roost.slnx`): `RoostGrammarLibrary` (loads the library from `ROOST_GRAMMAR_LIBRARY`, beside the application or the default search, ABI 1.x), `GrammarTokenizer`, `GrammarMatcher`, `GrammarSlots` (the masks behind C2's `grammar_slot`, computed on thread-pool threads) and `GrammarSampler` (masks applied in `CpuOps.Sample`, each token committed). Its tests skip without a built library; with one, they show that masked tokens are never sampled and that every output of roost-tiny and roost-tiny-moe under three JSON schemas parses and satisfies its schema. `Starlings.Roost.Server` reads `response_format` and `text.format` (`text`, `json_object`, `json_schema`) and refuses other types by name; `Starlings.Generation.Roost` adds `RoostChatClientOptions.Grammar` and compiles JSON formats with it (an unsupported schema keyword is a 400 with the engine's reason), then still refuses them, because no contract carries masks to the worker yet. `response_format` stays `unsupported`; the engine row is `untested`. llguidance and its 106 crates.io dependencies are in `THIRD-PARTY-NOTICES.md` and `PROVENANCE.md`.

### Changed

- `Starlings.Tokenizers` is a direct, exact pin (`[0.3.0]`, the version the Starling 0.3.0 packages require) in `Starlings.Generation.Roost` and `Starlings.Roost.Generation`, because `Starlings.Tokenizers.Tokenizer` is in the public API (`RoostModelProfile`); it was only transitive before, so `tools/check-roost-boundaries.py` never saw it.
- `Starlings.Roost.Generation`: `Qwen35RoostChatTemplate` builds a `Qwen35ToolCall` from the cloned arguments element directly instead of enumerating and re-serialising its properties. Same rendering.
- Documentation: the generation layer's status, build plan section 3.1 and its section 12 risk, and the kickoff log record that Starling published `Starlings.Models.QwenChat`, `Starlings.Models.Kev` and the public `StopSequenceMatcher` in ai-dotnet 0.3.0 (starling#124), and that `RoostCapabilities` carries `stop_sequences` as `untested`; `evidence/registry/README.md` states what the Qwen3.5-0.8B admission records for the tokenizer asset (`report_to_starling.status = "not needed"`).
